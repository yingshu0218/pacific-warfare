## 1. 使用方式与完成定义

每次选择一个前置条件已满足的任务，读取其输入和相关代码，完成实现、针对性验证与修复，更新状态后继续已授权范围。任务过大时可拆为 Txx.1、Txx.2，必须保留父任务的完整验收条件。不要把一个编号扩展成重新规划全项目。

任务表中的路径是建议修改范围，不代表文件已经存在。既有模型和演示作为输入复用，不能仅因以前做过相似展示就把新任务标为完成。测试名称为建议名，T01 建立统一验证入口后登记实际命令。

状态只使用：未开始、进行中、待验证、通过、受阻、后置。受阻必须写明具体依赖或故障及已完成部分；通过必须有交付证据。普通实现任务不要求逐项等待用户审批，已明确要求监督验收的资产继续遵守原要求。

一项任务的完成条件：

1. 行为和接口在指定使用场景成立，范围外代码未被无关重写。
2. 相关机制检查通过；视觉任务有原生截图，运动任务有短视频或连续帧。
3. 集成入口能读取该能力；纯数据任务有至少一个消费方或受控验证入口。
4. `docs/deliveries/<任务ID>.md` 写清文件、运行方式、检查结果、简化、遗留问题与资源清理；状态表更新。

## 4. 资产任务

军舰资产遵守[军舰模块化规范](standards/ship-modeling.md)，所有资产遵守总体规划的简化标准。具体型号和当前状态见[首版单位名单](unit-roster.md)。新型号先确定具体配置与关键尺寸，使用可重复生成的网格／场景、少量材质和稳定挂点。资料明确、比例估计和未知值分开记录。

每个具体型号先交付符合[参考图规范](standards/modeling-references.md)的参考任务卡：目标配置、已实际看过的精选整机／整舰图、每图用途与限制、角度覆盖和缺口，再进入依赖这些资料的建模。资料卡作为对应 A 任务的子项，不另增全局前置或用户审批。不能把文件数量、折翼照、施工照或异型照片当成完整主体参考。示例见 [SB2C-4](references/bombers/sb2c/modeling-brief.md)。

资料包按[统一视觉目标](art-direction.md)增加 Image Gen 阶段：原始资料与结构约束 → 统一风格主图及核对 → Godot 粗模和同模型多角度 → 必要补充目标图 → 简化模型交付。已有样件优先用自身粗模截图参与外观处理。生成图可指导细节取舍和材质，不改变历史尺寸、装备数量或原任务依赖，也不以风格图完成代替模型验收。

A01–A04 中所有军舰共用硬性验收：舰体、上层建筑外观形状与选定日期资料一致；主炮、副炮的炮型、炮座数、每座炮管数和位置逐座符合。专用防空炮数量可按游戏规模另配，参考卡保留历史基准与游戏清单，说明差异及承载／射界；兼任防空的主副炮仍固定。AI 生成图不能自行授权数量或位置变化。

单个型号的交付顺序固定为：主要轮廓 → 必要部件与安装 → 原生检视／机制检查 → 使用场景装配 → 浏览器集成。一次只完成表中一个具体型号再做下一款；任务表中的成对列举不要求同时制作。

## 5. 首批任务的具体执行单

### T01 项目盘点与验证入口

- 读取：`AGENTS.md`、本清单 G0、根工程／机场／衣阿华配置、现有测试和交付记录。
- 盘点：运行入口、资源根与软链接、可复用模型、导出模板、现有脚本错误、版本控制恢复方式；不清理不认识的文件。
- 实现：最小 Python 包装脚本，用明确工作目录运行 Godot，设置超时、日志和进程归属，失败后清理自己启动的进程。先支持导入和指定机制脚本，不搭完整 CI 平台。
- 验证：一次导入、一个现有机制测试、一个受控失败、一个超时；失败必须能识别，不能吞掉错误后返回成功。
- 交付：资产状态表、可复用验证命令、已知导入问题和 T01 记录。当前测试失败就记录并修复本任务所依赖的问题，不顺便重建所有模型。

现有可用基础命令如下，由包装脚本施加超时与日志；本次规划没有执行这些验证：

```sh
GODOT=/Applications/Godot.app/Contents/MacOS/Godot
"$GODOT" --version
"$GODOT" --headless --path . --editor --import --quit
"$GODOT" --headless --path . --script res://tests/test_weapon_motion.gd
```

### T02 最小数据与接口契约

- 先定义 `UnitDefinition`／`UnitState`、`WeaponDefinition`／`WeaponState`、`AmmoDefinition`、`MountSocket`、`BattleCommand`、`BattleEvent`、`ScenarioDefinition`；名字可按现有约定调整，职责不合并成一个巨大字典。
- 只填写一艘现有舰、一架现有飞机、一种舰炮和一种机枪／机炮所需字段，其他武器后续扩展，不一次建立全军数据库。
- 命令首批包含设定航行／飞行任务、指定目标和停火，返回接受／拒绝及原因；转炮和发射属于单位内部执行。
- 事件首批包含发射、命中、受损、失效、任务变化；包含实体／武器 ID、模拟时间和必要位置，效果参数由表现配置派生。
- 测试重点是引用完整、数据合法与实例隔离。任何尚未验证的历史参数标记估值；不为了类型定义引入复杂序列化框架。

### A01 现有模型接入准入

- 逐个登记现有入口和接口。先选择可用的主炮、A6M5a／F6F-5 与一艘主力舰，为 T04 提供最小组合。
- 明显错误轮廓、漂浮炮位、炮口方向反向、缺必要挂点属于修复范围；铆钉、细孔、精细栏杆、内舱不属于本轮工作。
- 军舰另交付舰体／建筑的同角度形状对照、逐座主副炮配置与位置表、防空历史基准和游戏配置差异。原型可供机制试验，未通过上述项目时继续保留正式资产未验收状态。
- 优先做外部适配，保留原检查场景；必要的公共 builder 修改需验证现有两个机型，不能只检查当前机型。
- 两个同型号实例应能有不同炮塔／起落架等状态。此处可验证接口运动，战斗判断仍由后续模拟负责。

### T03 固定世界与 T04 可见入口

- T03 先在不加载模型的条件下运行，验证种子、时间、暂停／倍速、事件清空和重置；单元失败用退出码报告。
- T04 只读取 T03 状态更新模型，接入自由／跟随观察和截图后退出；不重新制作舰船和飞机。
- 建立可见测试入口后确认模型装配与尺度，再做一次Chrome加载；这个检查只证明入口可用，不替代后续战斗或规模验收。
- 第一轮交付应能让用户看见已有舰机在统一世界里运行，并能稳定重置；不要求此时完成空战。

## 7. 交付记录与接续方式

交付记录保持简短，至少包含：

```text
任务与状态：
结果：用户现在能看到／使用什么。
修改：核心文件与接口变化。
验证：实际执行的命令、结果、证据路径。
简化：本轮采用的近似与后置细节。
问题：仍未完成的项及影响。
清理：本轮窗口、标签、服务和进程是否结束。
下一项：已满足依赖的任务及必要交接信息。
```

同一失败如果涉及公共接口，先修源头，再做最小相关回归；不要在每个模型或场景各打一份补丁。无关模型细节归后续资产记录，不扩展当前任务。

一个任务通过后，原则上冻结其接口和表现级别；新任务发现真实问题时再修。常规机制与代码检查由 Codex 执行，用户主要在 G3、G5 和 G6 判断整体观感、行为与规模是否符合目标。用户的反馈直接更新范围，不另设强制逐项批准流程。

## 8. 验证层级与性能预算

| 层级 | 何时使用 | 证据 |
| --- | --- | --- |
| 数据／机制 | 时钟、弹道、选敌、编队、弹药、队列、损伤修改 | 可控输入、关键状态与退出码；不写死某秒必定击落 |
| 原生画面 | 模型接口、活动部件、相机与效果修改 | 自动截图或短序列，核对尺度、连接和运动；完成后退出 |
| 浏览器集成 | 相关模块装配后，阶段入口或导出发生变化 | Chrome 的加载、输入、声音、错误与帧时间 |
| 长时／规模 | G3 初测、G5 完整复测与 G6 验收 | 明确舰机数量和在空数、弹丸／效果峰值、仿真进度、帧时间、内存方法和重置统计 |

基准统一为 M5／16 GB、内部 1440×900、1× 仿真，记录实际 canvas 像素、DPR、浏览器版本、种子与镜头序列。最低建议 p95 帧时间不超过 33.3 ms，目标 60 FPS；不能用关闭大半模拟单位获得帧率后宣称目标规模通过。

预算不足时按测量减少重复网格／材质、可见效果、非关键近景细节、声源数或无意义更新。不能丢掉模拟弹丸、减少库存消耗、修改伤害或使未被观看的交战停下来。
