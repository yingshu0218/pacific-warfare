## 可重复入口

在仓库根执行；用户手动运行的会话以 Ctrl-C 停止。所有引擎和服务经过 `verify.py` 互斥、归属、超时与进程组清理。

```sh
python3 tools/run_first_playable.py native --seconds 1200
python3 tools/run_first_playable.py web --build --seconds 1200
```

第二条在忽略目录构建，然后启动[本地观战页](http://127.0.0.1:8765/index.html)。`tools/preview_web.sh --seconds 1200` 是同一入口。**当前已有 `build/first-playable` 是冻结旧航空的音频对照包，不能作为 S04／S09 最终版本；集成完成后必须用 `--build` 重建。** 根工程默认大和入口没有改动。

只构建／审计／分析：

```sh
python3 tools/build_first_playable.py --owner S08
python3 tools/audit_first_playable_pack.py
python3 tools/summarize_s08.py
```

可复验的报告模式（服务主动启动后访问）：

`http://127.0.0.1:8765/index.html?measure=review-chrome&limit=900`

普通 URL 不启用采样、音频旁路录制或内部诊断。报告来自实际 rAF、Godot 帧和世界状态，只回传同源 localhost；没有注入战果或代替实际 tick。截图按钮只在报告模式存在。页面和服务均有独立上限；页面到期退出引擎并转为空白，服务到期关闭监听。自动验收的测试标签另由 CUA 关闭。

## 实测与性能界限

Apple M5／16 GiB、macOS 26.6.2。Chrome 实际 UAData 为 **157.0.8103.39，arm／64**。两个 Chrome 短跑均为种子 707、原 S07 自动摄影规则、Compatibility、真实 WebGL buffer **1280×720**、DPR **2**；CSS 为 **1712×963**，浏览器内容区域 1800×963。镜头 ID、标签及优化后位置在逐秒记录中。没有用 headless FPS 代替浏览器。

下表统一取首局、自动镜头、1×、未暂停、可见、仿真 10–60 秒；前 10 秒为热身。截图及操作造成的长帧保留在原始数据中，因此不是理想化的纯 GPU 测量。

| Chrome 实际样本 | 帧数 | p50／p95／p99 ms | >33.333 ms | 绘制调用范围 |
| --- | ---: | --- | ---: | --- |
| `clean-baseline/chrome-clean`，合并前，静音 | 3533 | 13.6／25.1／33.1 | 0.764% | 381–2713 |
| `chrome-audio/chrome-audio-fixed`，合并及音频修复后 | 4041 | 9.9／24.2／33.36 | 1.015% | 151–1153 |

后者 10–60 秒主要仍静音，约 64.5 秒才实际启用声音；包含一次截图操作。两组相同自动摄影规则，帧投递时刻不同，不能称逐帧完全相同相机轨迹。近距空战阶段 p95 为 24.61→20.4 ms；主炮阶段则为 24.5→33.225 ms。**只能证明短样本和批处理收益，不能据此宣布新航空／地图版本稳定 30 FPS。** 没有据短样本修改任何阈值。

两组真实弹丸峰值均 **1174**，炮位 **152**，单位 **12**；效果分配峰值 **311**，没有显示池丢弃。Chrome 修复短跑最大积欠约 **0.01656 秒**，不足一个固定 tick；没有删 tick。CPU 平均模拟推进约 5.22 ms／帧，未据此修改舰队／战斗热路径。

内存口径分别保存，不能相加：

- 合并前 WASM 线性内存为 **104726528 B**，后者为 **125698048 B**（约 120 MiB），各自短样本中固定。它是保留的线性堆容量，不是整进程物理内存。
- 修复 Chrome 的 JS used heap 约 **28.1–50.6 MiB**，有 GC 波动。
- 时间关联的页面 Renderer PID **3645**，物理占用峰值约 **428 MiB**，收尾活动区约 **383–395 MiB**；Chrome 主进程约 **124–126 MiB**。扩展、其他 Renderer、GPU 等仍分别留在原始进程记录，没有冒称这些数字是整浏览器总量。PID 归属根据启动／页面负载变化推断，非 CDP 的强绑定。

## 实际音频缺陷与对照

历史 Safari 候选页确实出现“因为使用了大量内存，此网页已重新载入。”，记录已移到 `candidate-before-spatial`，不是最终通过证据。当前用户已取消 Safari 验收，后续不再打开它。

固定模板的 sample `pause(false)` 直接进入恢复／重建 source；原观战代码每帧重复设置暂停属性。实测说明只加暂停 guard 仍不足以解决原生 sample 图的增长：

| 历史诊断包 | 实际 native AudioBufferSource 创建 | 进程物理占用结果 |
| --- | --- | --- |
| `audio-before` | 约 39.6 仿真秒累计 **14668** | 452.7→3395.9 MiB，失败 |
| `audio-after`，仅 guard | 约 41.4 秒 **470**，后续仍增长 | 峰值约 1199.3 MiB，未通过 |
| `audio-stream`，guard＋Web stream | **0** | 活动暖机后约 644–719 MiB；因用户新指令结束，不能代替长测 |

最终 Chrome 短确认有 **157 个连续样本**，真实 source 创建数全程 **0**，WASM 固定，未发生重载或未处理页面／控制台错误。实际启用声音的有效采样约 51 秒；全局观测输出峰值 **0.1934**，并保存从真实输出旁路录得的 **7.92 秒、48 kHz 双声道 Opus** 文件。该片段峰值约 -33.84 dBFS、RMS 约 -55.36 dBFS，表现为当前远距摄影下的低音量；不是拿合成源文件当实际播放证据。`audio_validation.json` 保存实际解码检查。

这证明本轮 Chrome 的爆增路径被避开且有真实输出；**未证明十分钟音频稳定、全部距离的听感或启用声音时暂停的正确性**。本轮观察到的 `(paused,sound)` 只有 `(false,false)`、`(false,true)`、`(true,false)`。Space 在声音按钮仍持有键盘焦点时可能同时触发声音按钮；留待最终 Chrome 操作验收修正／复验，不再为此新增短跑。
