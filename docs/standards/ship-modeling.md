# 军舰模块化建模规范

本规范适用于所有军舰，包括大和号、衣阿华级及后续舰型。新建模型必须遵守；现有模型按模块逐步迁移，不以一次重写阻塞正在进行的形体校正。固定 Godot 4.7.2、Compatibility、带类型 GDScript。

## 第一版简化范围（2026-11-10）

本规范约束模块责任、装配、接口与资料标注。用户最新要求是还原舰体和上层建筑的外观形状，同时简化表面细节与内部机械。铆钉、细孔、内部机构、细密栏杆、复杂索具与不影响外形的附件后置。资料不足的近似几何须标记未核实，不能据此通过外形或主副炮位置验收；不能用虚构支撑掩盖安装错误。

### 外形与武器的固定要求

| 对象 | 必须满足 | 允许简化／调整 |
| --- | --- | --- |
| 舰体 | 与所选舰名和日期的外形一致：长宽比例、艏艉轮廓、舷侧曲面、甲板边界与高低变化 | 表面刻线、细孔、纹理及内部结构 |
| 上层建筑 | 舰桥、舱体、烟囱、主要桅杆和平台的外轮廓、体量、比例、层级及位置一致 | 不改变外形的小附件、表面细节与内部机构；不能改成通用积木轮廓 |
| 主炮与副炮 | 炮型、口径、炮座数量、每座炮管数量和安装位置完全符合所选历史配置；逐座核对中线／舷侧关系、甲板层级、炮座中心及承载结构 | 炮塔表面和内部机构；不得因游戏性或性能增减、移位、改联装形式 |
| 专用防空炮 | 炮型和外形具有时代依据，安装与射界合理 | 数量可按游戏规模、演出和性能配置；优先沿用真实炮位，记录游戏配置与历史编制的差异 |

兼具防空用途、同时属于主炮或副炮编制的高平两用炮，按主副炮固定要求执行，不因具备防空能力而自动进入可调整数量的范围。每舰参考任务卡明确各炮型的归类。

历史编制与游戏防空配置分别保留，不覆盖史料记录。游戏采用的实际防空炮位清单须与模拟中的火控、弹药、炮口和损伤一致；降低远景模型或特效数量属于表现优化，不自动改变实装炮位或火力。

舰体与上层建筑外形对照、主副炮编制和逐座位置检查通过，且连接与接口可用后，进入正式整舰和系统集成。中性近景用于检查结构，不以缺少微小细节判定首版不通过。历史估值继续标记；未核实的形体或炮位可用于明确标注的原型测试，不能标为正式模型验收通过，也不阻塞独立机制工作。

## 1. 模块划分

| 模块 | 负责内容 | 不应包含 |
| --- | --- | --- |
| 舰体 Hull | 外板、甲板、艏艉、球鼻艏、水下附体及甲板安装面 | 上层建筑、武器几何 |
| 上层建筑 Superstructure | 舰桥、舱室、烟囱、桅杆、连续建筑甲板、真实外伸平台 | 炮塔、炮管、为补悬空临时拼出的支柱 |
| 炮塔底座 MountFoundation | 真实炮座/座圈支承、固定安装基座、与承载面衔接部分 | 回转炮室、俯仰枪炮组件 |
| 炮塔或炮架 WeaponMount | 回转炮室/炮盾、炮架、摇架、炮管、供弹与操作机构 | 舰体专属平台、船上大段承载建筑 |
| 其他装备 Equipment | 独立武器、雷达、测距仪、探照灯、舰载艇、弹射器、吊机等 | 整舰布局、相机、模拟指挥逻辑 |

小口径武器同样分离承载结构、固定安装底座和运动炮架；不得因为没有封闭炮塔就绕过模块接口。不是每种武器都存在高炮座或外露柱体，禁止为统一外观虚构底座。大型底座上的共用技术部件与舰体专属适配部分分开保存。

上层建筑内部也要按舰桥、烟囱、桅杆、平台等拆分，不能把全部几何写成一个不可独立检查的整舰生成函数。

## 2. 场景装配与运动层级

```text
ShipRoot
├── Hull
├── Superstructure
│   ├── Bridge
│   ├── Funnel
│   └── Platforms
├── MountFoundations
│   └── Foundation_<station_id>
│       └── WeaponInstance
│           └── TrainPivot
│               ├── HousingAndControls
│               └── ElevationPivot
│                   └── GunsAndCradle
└── Equipment
```

层级表示责任与运动归属，不要求把多个武器绑成同一个场景。安装时以承载模块暴露的安装点计算 Foundation 的变换；安装点始终有明确宿主，不能仅凭整舰坐标猜测。舰体专属平台归上层建筑，不能打包进通用武器素材。

炮衣、装填平台、测距仪等按真实机构决定固定、回转、俯仰或联动归属，不允许将整套附件一律挂到俯仰轴。并联炮管若实际独立俯仰，应分别设轴。

## 3. 坐标、原点与接口

- 全部模型按米制 1:1 创建，实例默认缩放为 `(1,1,1)`；禁止靠非等比缩放迁就舰型。
- 延续本项目坐标：+X 右舷，+Y 向上，-Z 舰艏/武器零位射向。整舰原点为选定基准水线的中纵剖面与舰长中点交点，使用何种舰长与载况必须记录。
- 独立武器根原点是安装面与回转轴交点；炮轴位置使用明确的局部偏移。固定底座下端为其宿主安装面，上端暴露 `weapon_seat`；二者有高度差时必须来自真实底座几何。
- 安装点用 Marker3D 或等价数据表示，至少记录稳定 `station_id`、宿主模块、局部 position/rotation、兼容接口、安装面尺寸/标高、资料来源及置信状态。
- 底座输出接口与武器输入接口需匹配：回转轴、座圈/基脚尺寸和甲板接触面。可用适配模块，但必须有真实结构依据，不能是任意补缝件。
- 视觉模型不自行创建相机、海面、UI或自动瞄准。运动参数、命令接口和演示控制独立，素材可在静态检视场景单独实例化。

## 4. 复用与目录

建议新模块使用：

```text
assets/naval/hulls/<class>/<variant>/
assets/naval/superstructures/<class>/<dated_configuration>/
assets/naval/foundations/<foundation_id>/
assets/naval/weapons/<weapon_id>/<mount_variant>/
assets/naval/equipment/<equipment_id>/
scenes/ships/<ship_id>/
data/ships/<ship_id>/<dated_configuration>.json
```

生成脚本可放 `scripts/naval/` 下对应分类。现有独立子工程可在自己的资源根下采用同样相对结构，不移动其他对话正在编辑的文件。

- 同型号武器引用同一资源，舰上仅保存实例变换与个体状态；禁止为每个炮位复制一份几何脚本。
- 单装、双联、三联，以及开放/封闭炮盾属于有来源的炮架变型，不能简单缩放同一个模型代替。
- 同级舰共享舰体与相同装备；舰别、年份、改装差异由装配清单选择模块表达，不能静默混合不同年代。
- 资源静态网格可合并或实例化优化，但不得跨模块边界、跨武器实例或跨运动轴不可逆合并。合并必须保留可单独调试的源模块。

## 5. 资料与建模顺序

1. 选定具体舰与日期；按[建模参考图规范](modeling-references.md)实际看过精选整舰图，建立高位／俯视、侧视、斜前／后及必要安装近景、关键尺寸来源表，记录异型／异期限制和缺口。
2. 完成舰体与连续上层建筑，确定真实甲板、舱室和外伸平台。
3. 标注安装点，核对其宿主和标高，再制作实际底座。
4. 安装共用炮塔/武器模块，检查座圈、底板、炮架、甲板之间的接触。
5. 补首版影响轮廓辨识或实际使用的其余装备，在组装场景验证安装关系与独立运动；微小附件后置。
6. 组装完成后，再开展浏览器兼容性、交互与性能测试；不在单个模块建模阶段反复启动浏览器。最后按需要开展材质和性能优化。

尺寸和位置必须区分已测量/资料明确、图像估算、未确认。缺少依据时记录缺口，不能用柱、斜撑、横梁或任意放大建筑去迎合旧炮位。不能以“没有悬空”替代真实结构复原；补接和碰撞检查都不能提供历史依据。

## 6. 模块验收

- 同一模型的侧、俯、斜视与选定日期资料对照：舰体和上层建筑外形一致；不能仅以“能认出舰型”通过。
- 主副炮逐座对应配置表，核炮型、炮座数、每座炮管数、位置及安装层级；数量正确不能代替位置正确。防空游戏配置另列差异及理由。
- 每个模块可独立加载，原点、朝向、尺寸及接口清楚，来源和许可随资源保存。
- 每座武器对应唯一安装点，安装点对应实际宿主面；底座两端接触正确，无明显穿插、悬空、重复底座和虚构支撑。
- 用俯视、侧视和近景实测装配，记录接触面的高度与尺寸；接触检查只是必要条件，仍需与史料对照。
- 确认同一武器素材可多次实例化且各实例运动互不影响，固定/回转/俯仰分组正确。
- 记录每个模块的未核实项；整舰测试通过不得覆盖模块几何缺陷或历史疑点。
- 测试顺序固定为：模块建模 → 原生模块检视及必要机制检查 → 整舰组装与安装验证 → 浏览器测试。原生截图、资源导入及必要机制检查可在建模阶段进行；浏览器测试须等相关整舰/使用场景组装完成后再进行。
- 测试尽量在后台执行：优先 headless 导入/检查、自动截图后退出、隐藏的临时浏览器标签；非必要不弹出编辑器或切换用户正在使用的窗口。Chrome 必须前台才能完成的检查仅在必要时短暂进行。
- 按用户 2026-11-10 最新要求，浏览器测试只使用 Chrome，记录 M5/16GB 上的实际表现；不再启动 Safari 测试。每轮测试结束，无论成功或失败，都关闭本轮创建的临时窗口、标签、预览进程、HTTP 服务和其他测试进程；先确认归属，不关闭用户原有窗口或无关服务。用户明确要求保留供查看的窗口除外。
- 自动截图预览应自动退出，测试命令应有合理超时和清理路径。不得留下空闲测试服务持续占用资源，也不得以“之后还可能要用”为由长期保留。

## 7. 现有模型迁移

优先把舰体、上层建筑、固定底座、可动炮架从整舰生成器中分离；保持现有船体坐标与炮位ID稳定。先完成一个可复用武器模块及一处有依据的完整安装，再迁移同型实例。拆分时校对局部/全局变换，不把旧估值升级为已确认数据。迁移进度与例外应写入各舰文档，不能宣称现有大和号、衣阿华已自动满足本规范。
